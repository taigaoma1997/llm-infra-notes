- 2026-10-12: Compared nano-vllm with mini-sglang by walking the same example through both: 1000 requests of 500 + 300 tokens, with room for 262,144 tokens of KV cache. The step loop is the same: prefill first, one kind of step at a time, K/V written before attention reads it, CUDA graph for decode. Four design choices differ, and they hang together. nano-vllm keeps 256 tokens per block and shares prefixes by hashing full blocks; mini-sglang keeps one token per slot, so its radix tree can share a prefix of any length, at the cost of a new slot for every request on every decode step and a slot table that lives on the GPU. nano-vllm admits a request with blocks for its prompt only and preempts when the cache runs out; mini-sglang reserves the prompt plus `max_tokens` at admission and never preempts, so in this example it is limited by the 256 rows of its page table, and with my laptop's 47,008 slots only 58 requests would fit at once. nano-vllm waits for each step's tokens before scheduling the next one; mini-sglang launches the next step first. And nano-vllm is one program, while mini-sglang is a server with three kinds of processes that streams tokens back. ## Learned

- Read the code repo thoroughly again, had a deeper understanding on the engine, scheduler, sequence, block manager, model_runner, etc.
- Chunked prefill, happens when a sequence is larger than the prefill token budget. 
- In nano-vllm, every step decide if needs prefill or decode. 
- Release block does not delete hash, it got deleted when others use it, so other seq can still hit the cache. 
- GPU is waiting for CPU postprocessing -> this is what over-lapping scheduling mini-sglang is doing. 
- nano-vllm v.s. mini-sglang, design choice ? 1 token per block (radix tree), reserve the token cache; overlapping; multi-processing services -> design is a combined set of decisions, need to balance between all aspects.
