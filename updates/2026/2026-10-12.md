- 2026-10-12: Compared nano-vllm with mini-sglang by walking the same example through both: 1000 requests of 500 + 300 tokens, with room for 262,144 tokens of KV cache. The step loop is the same: prefill first, one kind of step at a time, K/V written before attention reads it, CUDA graph for decode. Four design choices differ, and they hang together. nano-vllm keeps 256 tokens per block and shares prefixes by hashing full blocks; mini-sglang keeps one token per slot, so its radix tree can share a prefix of any length, at the cost of a new slot for every request on every decode step and a slot table that lives on the GPU. nano-vllm admits a request with blocks for its prompt only and preempts when the cache runs out; mini-sglang reserves the prompt plus `max_tokens` at admission and never preempts, so in this example it is limited by the 256 rows of its page table, and with my laptop's 47,008 slots only 58 requests would fit at once. nano-vllm waits for each step's tokens before scheduling the next one; mini-sglang launches the next step first. And nano-vllm is one program, while mini-sglang is a server with three kinds of processes that streams tokens back. Q&A in Chinese, the same page in both folders: [mini-sglang](../../notes/mini-sglang/QA-vs-nano-vllm.md), [nano-vllm](../../notes/nano-vllm/QA-vs-mini-sglang.md).
- 2026-10-13: Before starting SGLang, compared it with mini-sglang, with nano-vllm alongside, on SGLang's main branch (`e9400c5`). mini-sglang keeps SGLang's skeleton: the same request path, the same split into processes, and the same four core mechanisms. It simplifies in two ways. On the core path, each step keeps only the simplest policy: first come, first served; one token per KV slot; one kind of KV pool; and a full reservation of `max_tokens` at admission, where SGLang counts running requests at a fraction of their remaining tokens that shrinks over time, and retracts the requests with the least output when that estimate turns out too low. And whole features are left out: quantization, speculative decoding, structured output, LoRA, multimodal models, PD disaggregation, hierarchical caching, data and expert parallelism, and RL weight updates. SGLang's runtime is about 108 times larger and has 527 server arguments to mini-sglang's 20. One finding ties back to my backlog: after inserting a prompt into the radix tree, SGLang writes the tree's KV indices back into the request's own table, which is exactly the step mini-sglang misses (A1). - 2026-10-14: Tested nano-vllm PR [#281](https://github.com/GeeeekExplorer/nano-vllm/pull/281), INT8 weight-only (W8A16) quantization with its own Triton kernel, which reports +7.3% throughput on an RTX 4070 Laptop GPU. - 2026-10-15: Started reading mini-sglang's code stage by stage, beginning with `overlap_loop`, which looks almost the same as `normal_loop`. The only difference is which batch's results each loop processes: the overlap loop launches step k and only then waits for step k−1, so step k is already queued on the GPU when k−1 finishes, and the CPU processes k−1 and prepares k+1 while the GPU computes k. The CPU waits in one place only, an event recorded right after each step's tokens are copied back, so it waits for that step and nothing launched after it. Step k+1 can be prepared before step k's tokens are known because each request's length is updated at launch and the input tokens are handed over in a GPU buffer. With several GPUs, each GPU has its own scheduler process that waits only for its own GPU. The GPUs wait for each other inside the communication calls (58 per step for Qwen3-0.6B), and the schedulers meet once per loop, when rank 0 broadcasts how many new messages there are, so that every rank schedules the same batch; PR #113's sort is there for the same reason. Q&A in Chinese: [notes/mini-sglang/QA-overlap.md](../../notes/mini-sglang/QA-overlap.md).
- 2026-10-17: Reproduced mini-sglang's radix-cache bug (backlog A1) end to end and filed it as [#168](https://github.com/sgl-project/mini-sglang/issues/168). First I traced it with prints in the scheduler: with overlap scheduling, the second of two requests that share a 300-token prefix is admitted before the first one's prompt is in the radix tree, computes the prefix again, and frees its own 300 pages when it inserts its prompt, while its page table still points at them. That alone changes nothing, since the pages keep their data until another request is given them. Getting them reused took some design: the admission check reserves room for the duplicate copy, so the two requests' own decode steps never reach the freed pages, but a third request, held back by the same check until the pages are freed, gets exactly those pages. My first prompts were repetitive, and the output did not change, because the answer did not depend on the overwritten positions. With a table of secret codes instead, the second request answers `' 23043555555'` instead of `' 2093.'`; with overlap scheduling off, with a larger KV cache, or alone, it answers correctly. Both open fixes, PRs #142 and #154, pass the reproduction. Neither had one before, and #154 does not mention #142. Write-up: [notes/mini-sglang/issues/168](../../notes/mini-sglang/issues/168-radix-dedup-stale-page-table.md).

### mini-sglang #168 ([write-up](../../notes/mini-sglang/issues/168-radix-dedup-stale-page-table.md))

### mini-sglang #170 ([write-up](../../notes/mini-sglang/issues/170-abort-in-flight-double-release.md))
- Root cause -> Two code paths release the same request (the abort in receive, and the result processing) and neither knows about the other, so the request is released twice.
- Why does overlap scheduling cause bugs like this? -> The CPU's bookkeeping is one step behind the GPU. Between launching a step and processing it, anything that changes a request's state (like an abort) must know the step is still in flight.
- Same bug, different symptoms -> With a cache hit, the double unlock makes ref_count −1 and crashes; with a miss, the root's unlock does nothing, but the second cache_req frees the request's own pages as duplicates. So test both cases.
- How to fix it -> Defer the abort's release until the in-flight step is processed (#111's pending_aborts), so every lock is matched by exactly one unlock.
- More interesting, how to find this new case? -> Asked whether the bug really needs its condition (EOS). It doesn't in prefill, and that case was the crash someone reported months ago.
- How to reproduce a timing bug without a load test -> Subclass the offline LLM and inject the abort at an exact loop iteration (override _forward and offline_receive_msg). The result is deterministic.
- Although bugs in overlap scheduling, but there are two different bugs, two fixes -> #111 doesn't fix #168 and #154 doesn't fix #170. Check which code each PR actually changes.
- Writing the issue -> We should use the general root cause, not one special case.
