- 2026-10-05: For nano-vllm [#190](https://github.com/GeeeekExplorer/nano-vllm/issues/190), looked inside the CUDA graphs nano-vllm records for decode, by dumping them with CUDA graph debug mode. The graph for batch size 1 has 395 nodes, 14 kernels per layer, and I could map each one to a step in the model. The graph for batch size 16 uses different kernels, not just bigger launches: matrix multiplies switch from matrix-vector to matrix-matrix kernels, and attention is no longer split into chunks. That is why nano-vllm records one graph per batch size. I also drew how the pieces connect: each recorded node points to a kernel and holds the addresses of the buffers it reads, which is why every step copies its inputs into fixed buffers, and why a table one column too wide breaks the copy. Then I quizzed myself on it. The gaps were about addresses (why the inputs must be copied into the buffers, and what `block_tables` actually holds), how empty seats avoid doing harm, and the fact that one long sequence fails the whole batch. I wrote six harder questions to work through next. Write-up: [notes/nano-vllm/issues/190](../../notes/nano-vllm/issues/190-cuda-graph-block-tables.md#inside-a-recorded-graph).

- 2026-10-06: Opened a docs PR to [triton-windows](https://github.com/triton-lang/triton-windows): [#56](https://github.com/triton-lang/triton-windows/pull/56). While working on #190, `torch.compile` kept failing on my laptop with `PermissionError: [WinError 5]`. The cause is a PyTorch 2.6 bug: when it restores Triton kernels from its compile cache, it creates the target folder and then renames a temporary folder onto it, which Windows does not allow, so every later run fails too. PyTorch 2.7 fixed it inside a larger PR, but nobody had reported it, and triton-windows's README, which pairs PyTorch 2.6 with Triton 3.2, did not mention it. I reproduced it in a fresh environment without nano-vllm, checked that the workaround (turning off the kernel copy in the compile cache) costs nothing on one machine, and added a Known issues entry. Write-up: [notes/triton-windows/issues/56](../../notes/triton-windows/issues/56-pytorch-2.6-os-replace.md).
- 2026-10-06: Reproduced nano-vllm #190 on unmodified upstream: with `max_model_len=512`, a sequence that grows past 512 tokens crashes the CUDA graph replay with `The expanded size of the tensor (2) must match the existing size (3)`. Then I tested the fix the issue suggests, one extra buffer column, on a branch of my learning copy: the crash only moves from 513 tokens to 769. The real gap is that nothing enforces `max_model_len`: the scheduler adds blocks, the table is rebuilt, and only the copy into the fixed buffer notices, because slicing past the end of a tensor clips silently. This is the same kind of bug as #274 and #279: a limit the code assumes but never checks. Write-up: [notes/nano-vllm/issues/190](../../notes/nano-vllm/issues/190-cuda-graph-block-tables.md#reproduction).
- 2026-10-07: Tested the open PRs for nano-vllm #190 with the same reproduction script. [#270](https://github.com/GeeeekExplorer/nano-vllm/pull/270) rejects a request whose prompt plus `max_tokens` exceeds `max_model_len`, which fixes the root cause. It never mentions #190, so I only found it by searching for `max_model_len`. Its catch: one bad request fails the whole `generate()` call, and requests queued before it stay in the engine. [#191](https://github.com/GeeeekExplorer/nano-vllm/pull/191) runs a step eagerly when the table would not fit: no crash, but the sequence grows past `max_model_len`, its extra buffer column is never used, and its length check syncs the CPU with the GPU on every step. To run #191 at all, I first took two files from upstream, because its base predates a transformers change. I also wrote down what the issue taught me beyond the bug: enforce a limit where requests come in and grow, guard every dimension of a CUDA graph buffer, and decide who pays for one bad request. No PR from me so far. Write-up: [notes/nano-vllm/issues/190](../../notes/nano-vllm/issues/190-cuda-graph-block-tables.md#fixes-compared-the-open-prs-tested).

- 2026-10-07: Ran mini-sglang three ways (an offline script, the chat shell, and the server with curl) and worked through how it fits together. A server runs three processes: the API server, a tokenizer process, and the scheduler, the only one that uses the GPU. Tokenizing has its own process so that the scheduler can keep feeding the GPU: on my laptop, tokenizing an 8,000-token prompt takes 28 ms, about 3.5 decode steps. There is only one detokenizer because it keeps state per request: a character split across two tokens can only be sent once both have arrived. For the KV cache, I followed one token from its slot in the page table to its bytes in GPU memory: one `torch.empty` call, 2 KiB per token per layer, written by a small CUDA kernel and read by FlashInfer through a list of slot numbers, with no copy. nano-vllm uses the same memory layout with 256-token blocks, because flash-attn's paged kernel requires blocks of a multiple of 256. I also walked the radix tree with real tokens. Q&A in Chinese: [processes](../../notes/mini-sglang/QA-processes.md), [KV cache and radix tree](../../notes/mini-sglang/QA-kv-cache.md).
