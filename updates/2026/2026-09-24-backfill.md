## Done

- 2026-09-20: Started reading nano-vllm and ran it end to end on an RTX 4060 Laptop GPU (8 GB) with Qwen3-0.6B, on Windows. Getting it to start on Windows took two changes: the `gloo` backend instead of NCCL, and `USE_LIBUV=0` (upstream [#261](https://github.com/GeeeekExplorer/nano-vllm/issues/261)). Setup: [notes/nano-vllm](../../notes/nano-vllm/README.md).
- 2026-09-24: Read the main code path and got a working picture of four parts:
  - Scheduler (`engine/scheduler.py`): prefill and decode never share a step, chunked prefill is allowed only for the first sequence of a step, and the youngest running sequence is preempted when blocks run out.
  - BlockManager (`engine/block_manager.py`): a paged KV cache of 256-token blocks, prefix caching through hashes chained block to block, and reference counts for shared blocks.
  - ModelRunner (`engine/model_runner.py`): turns sequences into flat tensors (`cu_seqlens`, `slot_mapping`, `block_tables`), sizes the KV cache from free GPU memory after a warmup pass, and captures one CUDA Graph per decode batch-size bucket.
  - The one custom Triton kernel (`layers/attention.py`, `store_kvcache_kernel`): each program instance copies one token's K and V into the cache slot given by `slot_mapping`.

## Learned

- Decode is limited by memory bandwidth and by KV cache capacity, not by the prefill token budget: `max_num_batched_tokens` only applies to prefill.
- A CUDA Graph records kernel launches on fixed buffers, not values. Variable context lengths still work because the attention kernel reads `context_lens` and `block_tables` at run time.
- In the LLM infra stack (hardware, kernels, compilers, inference engine, serving), nano-vllm sits almost entirely in the inference-engine layer. It writes one kernel, calls flash-attn for attention, and uses `torch.compile` only on small elementwise pieces (RMSNorm, SiLU-and-multiply, rotary embedding, the sampler), not on the whole model.
